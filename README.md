# Pipeline + Underwater Monitoring — Phase 1 (Backend Core)

This is Phase 1 only: backend + inference engine + a bare-bones test
page. Real frontend UI comes in Phase 3. The point of this phase is to
get the data pipeline rock solid before any styling work happens.

Built with **FastAPI** (not Flask) — native async WebSocket support,
no socket.io protocol overhead, and free interactive API docs at
`/docs`.

---

## 1. Setup

```bash
cd pipeline_project
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

pip install -r requirements.txt
```

## 2. Add your trained models

Copy your two `best.pt` files here and rename them exactly:

```
models/pipeline_best.pt      <- your crack/corrosion/rust model
models/underwater_best.pt    <- your coral/debris model
```

If a model file is missing, the app will tell you exactly which one
and where it expected to find it (it won't crash silently — this is
tested, the error message comes back cleanly over both the upload
endpoint and the webcam WebSocket).

## 3. Run

```bash
python app.py
```

or, the more standard way to run FastAPI apps in development:

```bash
uvicorn app:app --host 0.0.0.0 --port 5000 --reload
```

Open `http://localhost:5000` in your browser for the test UI, or
`http://localhost:5000/docs` for the interactive API documentation
(auto-generated by FastAPI — worth showing your mentor, it documents
the upload endpoint's request/response shape for free).

## 4. Test it

**Upload test:** pick a video, choose the module (pipeline or
underwater), click Process Video. Wait — for CPU-only machines this
can be slow for longer videos, that's expected and we'll add frame
skipping if needed.

**Webcam test:** click Start Webcam, allow camera permission in the
browser. You'll see your raw feed (hidden) and the annotated result
coming back from the server every ~200ms. Click Stop Webcam when done
— this is important, it's what finalizes and saves the session data.

## What happens behind the scenes

Every time you process a video OR run a webcam session:

1. A unique `session_id` is generated (e.g.
   `pipeline_upload_20260617_140532_a1b2c3`)
2. A folder is created at `sessions/<session_id>/` containing:
   - `detections.csv` — every single detection, frame by frame, with
     a `track_id` column so you can count UNIQUE defects later instead
     of counting the same crack 300 times across 300 frames
   - `annotated_output.mp4` — the video with bounding boxes drawn (upload only)
3. One summary row gets **appended** (never overwritten) to
   `sessions/sessions_summary.csv` — this is the master file every
   future session adds a row to. This is what will power comparative
   analytics across sessions in Phase 2 (e.g. "has Section A's
   integrity score gotten worse over the last 5 inspections?").

## Why upload and webcam share the same code

Both `/api/process_video` and the WebSocket handler in `app.py` call
`run_detection_on_frame()` in `inference_engine.py`. Same severity
rules, same zone logic, same CSV schema. This matters: if upload and
webcam produced differently-shaped data, you couldn't compare them
later, which defeats the point of the comparative analytics phase.

## WebSocket protocol (for the webcam feature)

FastAPI's native WebSocket is used at `/ws/webcam` — no socket.io
library needed on either the frontend or backend. It's a plain JSON
message protocol:

```
Client -> Server:
  {"type": "start", "module": "pipeline"}
  {"type": "frame", "image": "data:image/jpeg;base64,..."}
  {"type": "stop"}

Server -> Client:
  {"type": "started", "session_id": "..."}
  {"type": "result", "annotated_image": "...", "detections": [...], "frame_number": N}
  {"type": "stopped", ...session summary...}
  {"type": "error", "error": "..."}
```

Detection (the CPU-heavy part) runs via `run_in_threadpool` so the
async event loop stays responsive to other requests while inference
is happening — this is one of the actual advantages of FastAPI over
Flask here: the upload endpoint and a webcam session could in
principle run concurrently without one blocking the other.

## Known limitation to flag to your mentor

Webcam frames are currently sent at a fixed rate (5 frames/sec,
configurable in `index.html` as `TARGET_FPS`) rather than the
browser's native framerate. This is intentional — running YOLO
inference on every single webcam frame at 30fps on a CPU-only machine
would queue up and lag badly. Sampling at 5fps keeps it responsive.
This is worth explicitly mentioning as a design decision, not hiding
it as a limitation — it's what a real system would also do on
constrained hardware.

## What's NOT in Phase 1 (coming next)

- Analytics engine (integrity index, severity breakdown, heatmaps,
  comparative trend analysis across sessions)
- Anomaly detection (IsolationForest)
- Real frontend UI (charts, dashboard, comparison view)
- PDF report generation

Phase 1's only job is: get video/webcam in, get clean structured CSV
data out, reliably, for both input types. Once you confirm
`sessions_summary.csv` is accumulating correctly across multiple test
runs, Phase 2 builds directly on top of it.
